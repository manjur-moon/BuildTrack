# Step 13D.3 — Personal notifications and activity history

## Usage
- Apply this patch to the Step 13D.2 project. No new dependencies or migrations.
- `/dashboard/notifications` is available to active verified organization members. Select **Check for alerts** to evaluate current scoped conditions and persist daily category summaries. Mark individual messages read/unread or all visible messages read. The inbox shows the unread count and paginates with 20 rows.
- `/dashboard/activity` requires current organization-level `audit:view` (owner or operational ADMIN). It lists existing audit metadata, supports search and pagination, and never returns raw before/after JSON, IPs, or arbitrary resource links.
- GET `/api/v1/notifications?page=1&filter=all|unread|read`; POST with `{action:"refresh"}`, `{action:"read-all"}`, or `{action:"set-read",id,read:boolean}`. GET `/api/v1/activity?page=1&q=...`. POST requires same-origin and verified session. GET returns no-store. Mutations are naturally idempotent: digest primary keys are deterministic and read-state updates do not create history. Concurrent opposing read-state updates use last committed state.
- Alerts use current task, project, inventory, report and expense scope queries. They store generic text, not amounts, counts, names, IDs or private report details; links open authorized modules, not raw URLs. Historical category alerts are hidden if the member loses that entire category permission. A historical alert may remain visible after partial scope reduction, but contains no old resource details.
- One digest per category/recipient/Dhaka date. Alerts are **pull-based**, not event-driven: assignment and report alerts cover the current local day; overdue, pending request, delay, low-stock and budget conditions reflect current records. No email, push, scheduler, cross-member fan-out, individual event linking, dismiss/delete, or top-bar count yet. Resource-linked legacy notifications are excluded rather than exposing stale access. These are known feature limits, not an assertion of final release readiness.
- Audit reads use current authorization and an explicit metadata projection; audit records are never mutated. Existing write audit coverage is not extended here. Personal read-state changes are not business audit events.

Integration test: set `DATABASE_URL` explicitly to local `buildtrack_auth_test` on port 5433, ensure migrations applied; set `RUN_NOTIFICATION_INTEGRATION=1`, run `npm run test -- tests/notifications/notifications.integration.test.ts`. The suite creates randomized isolated tenant fixtures and retains append-only audit records. Never run against development or production. Clear both temporary environment variables after tests.
